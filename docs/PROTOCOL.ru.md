# Спецификация протокола Wireline

Версия: 1
Статус: стабильна для v1. Любое изменение формата кадра требует повышения версии.

## 1. Назначение

Wireline — небольшой бинарный протокол запрос-ответ для аутентифицированного обмена
сообщениями поверх TCP, а в режиме надёжности — поверх UDP. Он существует, чтобы граница
сообщения, порядок байтов, проверка целостности и проверка подлинности были заданы явно,
а не спрятаны в библиотеке.

В область задач входит:

- кадрирование поверх потока байтов, который не сохраняет границы сообщений;
- целостность каждого кадра (CRC32) и подлинность каждого кадра (HMAC-SHA256);
- явный автомат состояний соединения с проверяемыми инвариантами;
- надёжность поверх UDP: ACK, повторная отправка, дедупликация.

Вне области задач: конфиденциальность. Wireline не шифрует. Шифрование делегировано TLS
(`ssl.SSLContext`), см. раздел 8.5.

## 2. Формат кадра

Все целые — big-endian, сетевой порядок. Без выравнивания и без дополнения
(формат `struct`: `!4sBBBIII`).

```
 0        4     5     6     7        11       15       19
 +--------+-----+-----+-----+--------+--------+--------+
 | magic  | ver | typ |flags|  seq   | length |  crc32 |
 +--------+-----+-----+-----+--------+--------+--------+
 |                  payload (length bytes)             |
 +-----------------------------------------------------+
 |         hmac-sha256 over header+payload (32)        |
 +-----------------------------------------------------+
```

| Поле | Размер | Смещение | Описание |
|---|---|---|---|
| magic | 4 | 0 | `b"WIRE"`. Отсекает чужих клиентов и рассинхронизацию потока. |
| ver | 1 | 4 | Версия протокола. Несовпадение — `ERR_VERSION`. |
| typ | 1 | 5 | Тип сообщения, раздел 3. |
| flags | 1 | 6 | Битовые признаки, раздел 4. |
| seq | 4 | 7 | Номер кадра отправителя, на соединение, строго возрастающий. |
| length | 4 | 11 | Длина payload в байтах. Лимит `MAX_PAYLOAD = 1 МиБ`. |
| crc32 | 4 | 15 | CRC32 только по payload. |
| payload | var | 19 | `length` байтов, может быть пустым. |
| mac | 32 | 19+len | HMAC-SHA256 по `header || payload` с общим секретом. |

Полный размер кадра: `19 + length + 32`.

Размер заголовка фиксирован, поэтому приёмник читает в три приёма: 19 байт заголовка,
затем ровно `length` байт, затем ровно 32 байта MAC. Значение `length` проверяется против
`MAX_PAYLOAD` **до** того, как будет выделен буфер такого размера (раздел 8.1).

## 3. Типы сообщений

| Код | Имя | Направление | Payload |
|---|---|---|---|
| 1 | `HELLO` | клиент -> сервер | JSON `{"client_id": str, "nonce": hex}` |
| 2 | `HELLO_ACK` | сервер -> клиент | JSON `{"session_id": str, "nonce": hex}` |
| 3 | `DATA` | оба | произвольные байты |
| 4 | `ACK` | оба | JSON `{"ack_seq": int}` |
| 5 | `PING` | оба | пусто либо произвольные байты |
| 6 | `PONG` | оба | эхо payload из `PING` |
| 7 | `ERROR` | оба | JSON `{"code": int, "message": str}` |
| 8 | `BYE` | оба | пусто |

Неизвестные значения типа отвергаются с `ERR_TYPE`. Новые типы могут появиться в следующей
версии; приёмник v1 не должен молча их игнорировать, потому что молчаливая терпимость
скрывает расхождение версий.

## 4. Флаги

| Бит | Имя | Значение |
|---|---|---|
| 0x01 | `FLAG_REQUIRE_ACK` | Отправитель ждёт `ACK` на этот `seq`. Используется в UDP-режиме. |
| 0x02 | `FLAG_RETRANSMIT` | Кадр является повторной отправкой ранее посланного `seq`. |
| 0x04 | `FLAG_COMPRESSED` | Зарезервирован, в v1 не реализован. Выставленный бит — ошибка. |

## 5. Автомат состояний

```
NEW --HELLO--> HANDSHAKE --HELLO_ACK--> READY --BYE--> CLOSING --> CLOSED
 |                 |                      |
 +-- timeout ------+-- bad_auth ----------+-- protocol_error --> CLOSED
```

Разница ролей:

- **Сервер** начинает в `NEW`. Корректный `HELLO` переводит сессию в `READY`, в ответ
  уходит `HELLO_ACK`. Состояние `HANDSHAKE` на сервере не занимается: проверка и ответ
  происходят за один шаг.
- **Клиент** входит в `HANDSHAKE` после отправки `HELLO` и остаётся там до получения
  `HELLO_ACK`. Именно здесь работает клиентский таймаут.

Инварианты, на каждый из которых должен быть отдельный тест:

| № | Правило | Результат |
|---|---|---|
| 1 | Любой кадр кроме `HELLO` в состоянии `NEW` | `ERR_STATE`, закрытие |
| 2 | Повторный `HELLO` в состоянии `READY` | `ERR_STATE`, закрытие |
| 3 | `seq` не больше последнего принятого от этого узла | `ERR_SEQ`, закрытие |
| 4 | Нет кадров дольше `idle_timeout` | закрытие без кадра `ERROR` |
| 5 | Неверный MAC | `ERR_AUTH`, закрытие |
| 6 | Любая `ProtocolError` при разборе | `ERROR` по возможности, закрытие |

У правила 6 есть оговорка: после ошибки разбора позиция в потоке больше не достоверна,
поэтому восстановление не делается. Соединение закрывается, процесс продолжает работать.

## 6. Коды ошибок

| Код | Имя | Причина |
|---|---|---|
| 1 | `ERR_VERSION` | `ver` не совпадает с поддерживаемой версией |
| 2 | `ERR_MAGIC` | `magic` не равен `WIRE` |
| 3 | `ERR_LENGTH` | `length` превышает `MAX_PAYLOAD` либо не совпадает с телом |
| 4 | `ERR_CRC` | Несовпадение CRC32 |
| 5 | `ERR_AUTH` | Несовпадение HMAC |
| 6 | `ERR_TYPE` | Неизвестный тип сообщения |
| 7 | `ERR_STATE` | Сообщение недопустимо в текущем состоянии |
| 8 | `ERR_SEQ` | Повторный или неупорядоченный номер |
| 9 | `ERR_FLAGS` | Выставлен зарезервированный или неподдерживаемый бит |
| 10 | `ERR_TIMEOUT` | Истёк таймаут простоя |
| 99 | `ERR_INTERNAL` | Непредвиденный сбой на стороне сервера |

## 7. Лимиты и таймауты

| Имя | Значение | Обоснование |
|---|---|---|
| `MAX_PAYLOAD` | 1 МиБ | Ограничивает единственную аллокацию, размер которой задаёт удалённая сторона. |
| `MAX_FRAME` | 1 МиБ + 51 | `MAX_PAYLOAD` плюс заголовок и MAC. |
| `idle_timeout` | 30 с | TCP-соединение может выглядеть живым долго после смерти процесса на том конце. |
| `handshake_timeout` | 5 с | Неаутентифицированное соединение не должно удерживать ресурсы. |
| `udp_rto` | 0.5 с | Фиксированный таймаут повтора в v1, см. ограничения. |
| `udp_max_retries` | 5 | Ограничивает суммарное время блокировки отправки. |
| `dedup_window` | 256 | Сколько последних `seq` помнить для каждого UDP-узла. |

## 8. Вопросы безопасности

### 8.1. Длина проверяется до аллокации

`length` — четырёхбайтовое поле, которым управляет удалённая сторона. Чтение тела до
проверки против `MAX_PAYLOAD` превращает 19 байт входа в попытку выделить 4 ГиБ. Поэтому
`decode_header` отвергает завышенную длину до того, как тело будет прочитано. Проверяется
тестом `tests/unit/test_codec.py::test_rejects_oversized_length_before_allocation`.

### 8.2. CRC32 не является средством защиты

CRC32 обнаруживает случайное искажение. Подобрать payload с совпадающим CRC тривиально.
CRC оставлен потому, что он дешёвый и быстро срабатывает на рассинхронизированном потоке;
свойство безопасности обеспечивает только HMAC.

### 8.3. HMAC и сравнение подписей

MAC покрывает и заголовок, и payload, поэтому `seq`, `type` и `flags` нельзя подменить
в пути. Сравнение делается через `hmac.compare_digest`; оператор `==` завершается на первом
несовпавшем байте и раскрывает длину совпавшего префикса через время выполнения.

### 8.4. Повторное воспроизведение

Перехваченный кадр остаётся корректным кадром. Защита — строго возрастающий `seq` в рамках
соединения плюс nonce в `HELLO`, который делает кадр из прошлой сессии невалидным в новой.
Поверх UDP тот же `seq` может законно прийти дважды как повтор, поэтому там приёмник
отбрасывает дубликаты по окну недавно виденных значений вместо разрыва сессии.

### 8.5. Своя криптография не пишется

Wireline не определяет схему шифрования. Конфиденциальность достигается запуском протокола
внутри TLS. Собственный шифр здесь был бы неверным ответом на уже решённую задачу.

## 9. Привязка к транспортам

| Транспорт | Что берётся у транспорта | Что даёт Wireline |
|---|---|---|
| TCP | порядок, повторы, контроль потока | кадрирование, аутентификация, автомат состояний |
| TCP+TLS | то же плюс конфиденциальность | то же |
| UDP | ничего сверх доставки по возможности | кадрирование (один кадр в датаграмме), ACK, повторы, дедупликация |

Поверх UDP кадр должен помещаться в одну датаграмму, поэтому практический предел payload
существенно ниже `MAX_PAYLOAD` и определяется MTU по пути.

## 10. Версионирование

`ver` проверяется на каждом кадре. При несовпадении приёмник отвечает `ERR_VERSION` вместо
попытки разобрать кадр по возможности: частично понятый заголовок хуже отклонённого
соединения. Совместимые расширения в пределах v1 ограничены новыми битами `flags` и новыми
полями внутри JSON-payload существующих управляющих сообщений. Любое изменение размера,
порядка или смысла поля требует `ver = 2`.
