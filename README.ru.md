# Wireline

Прикладной бинарный протокол поверх TCP с явным форматом кадра, явным автоматом состояний
соединения и набором тестов, покрывающих типичные ошибки кадрирования.

Спецификация протокола находится в [docs/PROTOCOL.ru.md](docs/PROTOCOL.ru.md) и написана
до кода. Английские версии: [README.md](README.md), [docs/PROTOCOL.md](docs/PROTOCOL.md).

## Что решает

TCP обеспечивает упорядоченный поток байтов, но не определяет границы сообщений, не
аутентифицирует стороны и не позволяет узнать, что процесс на другой стороне завершился час
назад. Wireline добавляет только эти три функции: кадрирование по префиксу длины,
HMAC-SHA256 на каждом кадре и автомат состояний с таймаутами.

## Формат кадра

```
 0        4     5     6     7        11       15       19
 +--------+-----+-----+-----+--------+--------+--------+
 | magic  | ver | typ |flags|  seq   | length |  crc32 |
 +--------+-----+-----+-----+--------+--------+--------+
 |                  payload (length bytes)             |
 +-----------------------------------------------------+
 |         hmac-sha256 over header+payload (32)        |
 +-----------------------------------------------------+
```

## Быстрый старт

Windows, PowerShell:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"

# терминал 1
$env:WIRELINE_SECRET = "local-dev-secret"
python -m wireline serve --port 9000

# терминал 2: $env: действует только в своём терминале, поэтому задаём ещё раз
$env:WIRELINE_SECRET = "local-dev-secret"
python -m wireline ping --count 5
python -m wireline send --text "hello"
```

- Команда `py` вызывает Python Launcher. Команда `python` без пути может запустить
  заглушку из Microsoft Store, которая выводит `Python` и ничего не создаёт.
- Если PowerShell не разрешает выполнить скрипт активации, используйте
  `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` (действует только в текущем
  окне).
- Активация не обязательна: `.venv\Scripts\python.exe -m pytest` работает и без неё.
- Опции указываются после команды: `serve --port 9000`, а не `--port 9000 serve`.

Linux и macOS: `python3 -m venv .venv && source .venv/bin/activate`, далее те же команды,
переменная задаётся через `export WIRELINE_SECRET=...`.

Ожидаемый вывод `ping`:

```
session 72f08a418fb6
pong 1/5  rtt=0.52 ms
pong 2/5  rtt=0.37 ms
pong 3/5  rtt=0.36 ms
pong 4/5  rtt=0.44 ms
pong 5/5  rtt=0.42 ms
```

Идентификатор сессии выдаётся заново при каждом подключении.

## Тесты

```powershell
pytest                        # всё
pytest tests/unit             # быстрые, без сокетов
pytest -m security            # только проверки свойств безопасности
pytest --cov=src --cov-report=term-missing
```

Тест-план с сопоставлением рисков и тестов находится в [docs/TEST_PLAN.md](docs/TEST_PLAN.md).

Три теста, с которых стоит начать знакомство:

- `tests/unit/test_framing.py::test_one_frame_delivered_byte_by_byte`: кадр приходит по
  одному байту и должен быть выдан ровно один раз, на последнем байте.
- `tests/unit/test_naive_reader_fails.py`: тот же вход подаётся в наивную реализацию через
  `read(n)`, которую обычно пишут первой, и эта реализация ломается.
- `tests/integration/test_tcp_session.py::test_split_frame_is_reassembled`: та же проверка
  через реальный сокет, с паузами, которые заставляют ядро отправить отдельные сегменты.

## Производительность

Замер выполнен на Windows 11 (сборка 26200), Python 3.13.3, loopback, эхо-приложение.
Команда запускалась дважды, в таблице указан диапазон между прогонами. Сырой вывод и
методика замера приведены в [docs/evidence/benchmark-loopback.md](docs/evidence/benchmark-loopback.md).

| Сценарий | p50 | p95 | p99 | Пропускная способность |
|---|---|---|---|---|
| последовательно, payload 1 КиБ, 2000 запросов | 0.15–0.17 мс | 0.26–0.35 мс | 0.45–0.55 мс | ~5200–6000 msg/s, 10–12 МБ/с |
| 100 параллельных клиентов, по 20 запросов | 9.6–11.4 мс | 18.7–22.7 мс | 19.4–25.0 мс | ~3900–4800 rps, 0 ошибок |

Выводы:

- Прогоны расходятся на 20–35% (p95 последовательного режима, rps под нагрузкой), поэтому
  одиночный замер на ноутбуке недостаточно надёжен.
- При 100 клиентах задержка одного запроса растёт в 60–70 раз (p50 с 0.16 мс до 10–11 мс),
  а суммарная пропускная способность не растёт и оказывается ниже, чем в последовательном
  режиме. На этой машине точка насыщения находится ниже 100 параллельных клиентов.
- Последовательная пропускная способность вычисляется как число запросов, делённое на сумму
  задержек, без учёта календарного времени. Паузы клиента между запросами в неё не входят,
  поэтому значение несколько завышено. Разница с параллельным режимом слишком велика, чтобы
  объясняться только этим.

Команда для повторения замера:

```powershell
python benchmarks/bench_tcp.py --requests 2000 --payload 1024 --clients 100
```

## TLS

Wireline не шифрует данные (ADR-0002) и для обеспечения конфиденциальности работает внутри
TLS.

```powershell
python tools/make_certs.py --out certs      # одноразовый самоподписанный сертификат
```

```python
from wireline.tls import server_context, client_context
server = WirelineServer(secret, ssl_context=server_context("certs/server.crt", "certs/server.key"))
client = WirelineClient(secret, ssl_context=client_context("certs/server.crt"),
                        server_hostname="localhost")
```

Рукопожатия TLS и Wireline проверяют разное и тестируются отдельно. TLS проверяет, что узел
является тем, за кого себя выдаёт, а Wireline проверяет, что узел владеет общим ключом.
В `tests/integration/test_tls.py` есть негативные случаи: недоверенный сертификат,
несовпадение имени узла, клиент без TLS против TLS-слушателя.

## UDP

```python
from wireline.transport.udp import UdpServer, UdpClient
```

Режим использует stop-and-wait, явный ACK, повтор по фиксированному таймауту и окно
дедупликации на приёмнике. Дедупликация нужна потому, что при потере ACK отправитель
повторяет запрос, который приёмник уже выполнил. Без неё слой надёжности приводил бы к
многократному выполнению одного запроса. Подробности и компромиссы описаны в
[ADR-0005](docs/adr/0005-stop-and-wait-over-udp.md).

Потери эмулируются генератором с фиксированным зерном, поэтому
`test_delivery_survives_forty_percent_loss` отбрасывает одни и те же датаграммы при каждом
прогоне.

## Анализатор трафика

```powershell
python -m wireline sniff tests/fixtures/tcp-session.pcap --flows
```

Анализатор разбирает захват по слоям L2 -> L3 -> L4 -> L7 и собирает сообщения Wireline по
каждому направлению TCP-соединения с помощью того же `FrameBuffer`, который использует
сервер. Модуль чтения pcap написан вручную: файл захвата состоит из заголовка и списка
байтовых строк с метками времени.

Разбор примера и порядок снятия собственного захвата в Windows и Linux описаны в
[docs/NETWORK.md](docs/NETWORK.md).

## Архитектура

Подробное описание приведено в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Кратко:

## Диагностика

| Симптом | Что проверить первым | Обычная причина |
|---|---|---|
| `ConnectionRefusedError` (`WinError 1225` в Windows) | запущен ли `serve` на этом адресе и порту | порт никто не слушает |
| `ERR_AUTH` на первом кадре | `WIRELINE_SECRET` с обеих сторон | у клиента и сервера разные ключи; в PowerShell `$env:` задаётся отдельно в каждом терминале |
| `ERR_MAGIC` сразу после подключения | кто именно подключается к порту | браузер, health check или занятый порт |
| клиент зависает и завершается по таймауту | `ss -tn` (Linux) или `netstat -ano` (Windows), состояние соединения | сервер запущен, но слушает другой интерфейс |
| соединение разрывается после ~30 с без трафика | лог сервера, строка `idle timeout` | штатное поведение; для поддержания соединения отправляйте PING |
| `ERR_SEQ` | повторяются ли кадры и не переупорядочены ли они | повторная отправка на уровне приложения либо реальный replay |

## Ограничения

Перечисленные ограничения приняты намеренно.

- Собственного шифрования нет. Конфиденциальность делегирована TLS, сервер и клиент
  принимают `ssl_context`. Вариант с собственным шифром отклонён в ADR-0002.
- В UDP-режиме нет скользящего окна и адаптивного RTO. Stop-and-wait с фиксированным
  таймаутом достаточно, чтобы показать компромисс. Оценка RTT по Джекобсону не реализована,
  поэтому пропускная способность ограничена одним круговым обменом на сообщение.
- Анализатор читает только классический pcap (не pcapng) и разбирает IPv4 поверх Ethernet
  или raw IP. Он не отслеживает номера TCP-последовательности, поэтому захват с
  переупорядочиванием или повторами на L4 нарушит сборку потока.
- Номера последовательности переполняются на 2^32, сессия при этом не переустанавливается.
- Секрет задаётся заранее, обмена ключами и ротации нет.
- `FLAG_COMPRESSED` зарезервирован и не реализован. Кадр с выставленным битом отвергается,
  а не игнорируется.
- Сервер работает в одном процессе, по одной задаче на соединение. Обратное давление
  (backpressure) обеспечивают только буферы сокетов ОС.

## Известные проблемы

Ниже перечислены открытые дефекты.

- Нет защиты от повтора между соединениями. Внутри соединения `seq` отвергает повторённый
  кадр, но целиком перехваченная сессия, повторённая в новом соединении, принимается,
  потому что nonce из `HELLO` не входят в MAC. Подробности приведены в PROTOCOL.ru.md,
  раздел 8.4, там же указан `xfail`-тест. TLS предотвращает сам перехват трафика.
- UDP-сессии не удаляются по истечении времени. `UdpClient.close()` не отправляет `BYE`,
  а у UDP-сервера нет таймаута простоя, поэтому для каждого адреса клиента, прошедшего
  рукопожатие, сессия и окно дедупликации хранятся в памяти до остановки сервера.
- UDP-клиент не сравнивает размер payload с пределом датаграммы. Payload больше примерно
  64 КиБ вызывает в `sendto` ошибку `OSError`, а не `ProtocolError`.

## Статус

Реализовано: спецификация, кодек, кадрирование, автомат состояний, TCP-сервер и клиент, TLS,
UDP-режим надёжности, анализатор pcap, CLI, наборы unit- и integration-тестов, бенчмарк.

Проверено на Windows 11 (сборка 26200), Python 3.13.3.

В качестве эталонного приложения используется эхо-сервис. Протокол не интерпретирует
содержимое `DATA`, а эхо является минимальным поведением, при котором работу транспорта
можно наблюдать.
