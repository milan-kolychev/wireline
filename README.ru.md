# Wireline

Прикладной бинарный протокол поверх TCP с явным форматом кадра, явным автоматом состояний
соединения и набором тестов, построенным вокруг того, как ломается кадрирование.

Спецификация — [docs/PROTOCOL.ru.md](docs/PROTOCOL.ru.md), написана до кода.
Английские версии: [README.md](README.md), [docs/PROTOCOL.md](docs/PROTOCOL.md).

## Что решает

TCP даёт упорядоченный поток байтов. Он не даёт границ сообщений, аутентификации и способа
узнать, что процесс на том конце умер час назад. Wireline добавляет ровно эти три вещи:
кадрирование по префиксу длины, HMAC-SHA256 на каждом кадре и автомат состояний
с таймаутами.

## Формат кадра

```
 0        4     5     6     7        11       15       19
 +--------+-----+-----+-----+--------+--------+--------+
 | magic  | ver | typ |flags|  seq   | length |  crc32 |
 +--------+-----+-----+-----+--------+--------+--------+
 |                  payload (length bytes)             |
 +-----------------------------------------------------+
 |         hmac-sha256 over header+payload (32)        |
 +-----------------------------------------------------+
```

## Быстрый старт

Windows, PowerShell:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"

# терминал 1
$env:WIRELINE_SECRET = "local-dev-secret"
python -m wireline serve --port 9000

# терминал 2: $env: действует только в своём терминале, поэтому задаём ещё раз
$env:WIRELINE_SECRET = "local-dev-secret"
python -m wireline ping --count 5
python -m wireline send --text "hello"
```

- `py` — лаунчер Python. Просто `python` может запустить заглушку из Microsoft Store,
  которая печатает `Python` и ничего не создаёт.
- Если PowerShell не даёт выполнить скрипт активации:
  `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` (только для текущего окна).
- Активация не обязательна: `.venv\Scripts\python.exe -m pytest` работает и без неё.
- Опции пишутся после команды: `serve --port 9000`, а не `--port 9000 serve`.

Linux и macOS: `python3 -m venv .venv && source .venv/bin/activate`, дальше те же команды,
переменная задаётся через `export WIRELINE_SECRET=...`.

Ожидаемый вывод `ping`:

```
session 72f08a418fb6
pong 1/5  rtt=0.52 ms
pong 2/5  rtt=0.37 ms
pong 3/5  rtt=0.36 ms
pong 4/5  rtt=0.44 ms
pong 5/5  rtt=0.42 ms
```

Идентификатор сессии новый при каждом подключении.

## Производительность

Замер на loopback с эхо-приложением. Полный вывод и методика —
[docs/evidence/benchmark-loopback.md](docs/evidence/benchmark-loopback.md).

| Сценарий | p50 | p95 | p99 | Пропускная способность |
|---|---|---|---|---|
| последовательно, payload 1 КиБ, 2000 запросов | 0.13 мс | 0.18 мс | 0.20 мс | ~7200 msg/s, 14 МБ/с |
| 100 параллельных клиентов, по 20 запросов | 9.6 мс | 9.9 мс | 10.7 мс | ~8800 rps, 0 ошибок |

Что из этого следует: при переходе к 100 клиентам задержка одного запроса растёт примерно
в 70 раз, а суммарная пропускная способность — на 20%. Это точка насыщения, дальше
увеличение параллельности ухудшает latency без выигрыша в throughput.

Повторить:

```powershell
python benchmarks/bench_tcp.py --requests 2000 --payload 1024 --clients 100
```

## TLS

Wireline ничего не шифрует сам (ADR-0002), он работает внутри TLS.

```powershell
python tools/make_certs.py --out certs      # одноразовый самоподписанный сертификат
```

```python
from wireline.tls import server_context, client_context
server = WirelineServer(secret, ssl_context=server_context("certs/server.crt", "certs/server.key"))
client = WirelineClient(secret, ssl_context=client_context("certs/server.crt"),
                        server_hostname="localhost")
```

Рукопожатие TLS и рукопожатие Wireline отвечают на разные вопросы и проверяются отдельно:
TLS — тот ли это узел, за который себя выдаёт; Wireline — владеет ли узел общим ключом.
В `tests/integration/test_tls.py` есть негативные случаи: недоверенный сертификат,
несовпадение имени узла, клиент без TLS против TLS-слушателя.

## UDP

```python
from wireline.transport.udp import UdpServer, UdpClient
```

Stop-and-wait, явный ACK, повтор по фиксированному таймауту и окно дедупликации на
приёмнике. Зачем последнее: потерянный ACK заставляет отправителя повторить запрос,
который приёмник уже выполнил, поэтому без дедупликации слой надёжности превращается
в размножитель запросов. Подробности и цена решения — в
[ADR-0005](docs/adr/0005-stop-and-wait-over-udp.md).

Потери эмулируются генератором с фиксированным зерном, поэтому
`test_delivery_survives_forty_percent_loss` отбрасывает одни и те же датаграммы на каждом
прогоне.

## Диагностика

| Симптом | Что проверить первым | Обычная причина |
|---|---|---|
| `ConnectionRefusedError` (`WinError 1225` в Windows) | запущен ли `serve` на этом адресе и порту | порт никто не слушает |
| `ERR_AUTH` на первом кадре | `WIRELINE_SECRET` с обеих сторон | у клиента и сервера разные ключи; в PowerShell `$env:` задаётся отдельно в каждом терминале |
| `ERR_MAGIC` сразу после подключения | кто именно подключается к порту | браузер, health check или занятый порт |
| клиент висит и отваливается по таймауту | `ss -tn` (Linux) или `netstat -ano` (Windows), состояние соединения | сервер поднят, но слушает другой интерфейс |
| соединение рвётся после ~30 с молчания | лог сервера, строка `idle timeout` | так и задумано, для удержания слать PING |
| `ERR_SEQ` | повторяются ли кадры и не переупорядочены ли они | повторная отправка на уровне приложения либо реальный replay |

## Ограничения

Каждое — решение, а не недоделка:

- **Своего шифрования нет.** Конфиденциальность делегирована TLS, сервер и клиент
  принимают `ssl_context`. Написание своего шифра отклонено в ADR-0002.
- **Нет скользящего окна и адаптивного RTO** в UDP-режиме. Stop-and-wait с фиксированным
  таймаутом достаточно, чтобы показать компромисс; оценка RTT по Джекобсону не реализована,
  поэтому пропускная способность ограничена одним круговым обменом на сообщение.
- **Анализатор читает только классический pcap**, не pcapng, и разбирает IPv4 поверх
  Ethernet или raw IP. Он не следит за номерами TCP-последовательности, поэтому захват
  с переупорядочиванием или повторами на L4 собьёт сборку потока.
- **Номера последовательности переполняются на 2^32**, сессия не переустанавливается.
- **Секрет предварительно разделённый**, без обмена ключами и без ротации.
- **`FLAG_COMPRESSED` зарезервирован и не реализован**; выставленный бит отвергается,
  а не игнорируется.
- **Один процесс, одна задача на соединение.** Backpressure ограничен буферами сокета.

## Известные проблемы

Ниже перечислены открытые дефекты.

- **Нет защиты от повтора между соединениями.** Внутри соединения `seq` отвергает
  повторённый кадр. Целиком перехваченная сессия, повторённая в новом соединении,
  принимается: nonce из `HELLO` не входят в MAC. Подробности — PROTOCOL.ru.md, раздел 8.4, и
  названный там `xfail`-тест. TLS не даёт перехватить трафик вообще.
- **UDP-узлы не устаревают.** `UdpClient.close()` не отправляет `BYE`, а у UDP-сервера нет
  таймаута простоя, поэтому каждый адрес клиента, прошедший рукопожатие, держит сессию и
  окно дедупликации в памяти до остановки сервера.
- **UDP-клиент не проверяет размер payload** относительно предела датаграммы; payload
  больше примерно 64 КиБ падает в `sendto` с `OSError`, а не с `ProtocolError`.
